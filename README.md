# Аналітика Spotify у MongoDB Atlas

Проєкт завантажує треки Spotify в MongoDB Atlas та виконує чотири запити: добірки для вечірки й фонової роботи, рейтинг виконавців і пошук нетипового темпу за жанром. [Умова курсу](https://www.edu.goit.global/learn/43680627/49489220/53071078/homework) · [Spotify Tracks Dataset](https://www.kaggle.com/datasets/maharshipandya/-spotify-tracks-dataset).

## Запуск

Потрібні Python 3.12, MongoDB Shell та кластер MongoDB Atlas. Ця версія використовує безкоштовний SpotifyStudy на AWS у Frankfurt. Перед підключенням у Atlas потрібно створити database user та додати поточну IP-адресу до Network Access. Рядок підключення з паролем зберігається тільки у власному .env.

Усі команди запускаються з кореня проєкту. Розпакуй датасет як `dataset.csv` поруч із README.

```sh
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
test -e .env || (umask 077; cp .env.example .env)
```

Заповни `MONGO_URI` у `.env`. Скрипти з LMS вибирають базу `spotify` і перебудовують колекції `tracks_raw` та `tracks`. Перед запуском перевір URI і використай окремий екземпляр або навчальний кластер із порожніми цільовими колекціями. Дані підключення не входять до пакета.

```sh
unset MONGO_URI
python scripts/01_load_data.py
mongosh --nodb --norc
```

Далі в mongosh:

```javascript
require("node:process").loadEnvFile(".env");
if (!process.env.MONGO_URI) throw new Error("Потрібен MONGO_URI у .env");
db = connect(process.env.MONGO_URI);
load("scripts/02_transform.js");
db = db.getSiblingDB("spotify");
load("queries/part2_queries.js");
load("queries/part3_indexes.js"); // додатковий експеримент, створює два індекси
```

За замовчуванням скрипт частини 2 показує кількості, повний топ-20 і зразки довших результатів. Щоб отримати весь результат одним об’єктом Extended JSON, запусти mongosh із `NOSQL_QUERY_OUTPUT=json` і виконай `load("queries/part2_queries.js")` після підключення. У цьому режимі не виконуй інші скрипти в тому самому виводі, якщо плануєш його обробляти автоматично.

## Імпорт і структура

Під час імпорту в Atlas із CSV на 114 000 рядків завантажилися 113 999 документів у `tracks_raw` і стільки ж у `tracks`. Один рядок пропущено, бо в ньому немає імені виконавця й назви треку. `track_id` — ідентифікатор Spotify; `_id` — ідентифікатор конкретного документа MongoDB. У колекції 89 740 унікальних `track_id`, тож рядок і трек — різні одиниці підрахунку.

Приклад із результатів (показано частину полів):

```json
{
  "track_id": "1a17Gt5Vh0HTKFCZr8Pctk",
  "track_name": "#Natural",
  "track_genre": "latin",
  "artists": ["Paty Cantú", "Juhn"],
  "duration_ms": 226605,
  "duration_sec": 226.6,
  "popularity": 0,
  "popularity_tier": "low",
  "audio_features": {
    "danceability": 0.791,
    "energy": 0.841
  }
}
```

**Чому аудіохарактеристики вкладені?** Енергія, гучність і темп описують той самий трек, тож їх можна читати та зберігати разом із ним без окремої колекції. Вкладеність відокремлює виміряні характеристики від назви й жанру; наприклад, `audio_features.energy` не плутається з метаданими треку. Фільтри та індекси однаково можуть звертатися до окремої характеристики за її шляхом. Якщо набір характеристик стане великим, часто оновлюватиметься окремо від треку або зберігатиме багато версій, вбудовування збільшить документи та ускладнить вибірку історії.

**Чому виконавці — масив?** У `#Natural` два окремі виконавці, хоча у вихідному CSV вони записані одним рядком. У MongoDB можна знайти треки за точним елементом масиву, а `$unwind` дає можливість зарахувати документ кожному виконавцеві окремо. Рядок із роздільником вимагав би повторного розбору або пошуку підрядка, що може дати збіг із частиною іншого імені.

## Додатково: індекси

Один прогін в Atlas `explain("executionStats")` із примусовим вибором планів для відтворюваного порівняння:

| Запит і план | Повернуто | Ключі | Документи | Етапи | мс |
| --- | ---: | ---: | ---: | --- | ---: |
| `pop` і danceability ≥ 0.7, сортування за популярністю; повне сканування | 354 | 0 | 113999 | SORT, COLLSCAN | 89 |
| Той самий запит; індекс | 354 | 412 | 354 | FETCH, IXSCAN | 2 |
| Фонова робота; повне сканування | 9324 | 0 | 113999 | COLLSCAN | 126 |
| Фонова робота; індекс | 9324 | 16602 | 16141 | FETCH, IXSCAN | 50 |
| `pop` і популярність ≥ 70, повні документи | 317 | 317 | 317 | FETCH, IXSCAN | 0 |
| Той самий фільтр, тільки поля індексу | 317 | 317 | 0 | PROJECTION_COVERED, IXSCAN | 0 |

Перший індекс `{track_genre: 1, popularity: -1, "audio_features.danceability": 1}` спочатку обмежує жанр. У межах жанру ключі вже впорядковані за популярністю, тому план обходиться без окремого сортування. Другий індекс починається з `explicit`, далі індексує instrumentalness і speechiness. Умову на loudness він не покриває, тому рушій зчитує документи та завершує фільтрацію після `IXSCAN`. Час одного запуску залежить від кешу й середовища; кількість ключів, документів і етапи точніше показують, що змінилося у плані.

Запит `find({track_genre: "pop", popularity: {$gte: 70}})` **не покривний**: індекс містить поля предиката, але повні документи вимагають `FETCH`. Якщо явно повернути лише `{_id: 0, track_genre: 1, popularity: 1}`, предикат і результат доступні з того самого індексу; план Atlas повернув 317 записів, не прочитавши жодного документа.

Код і технічний опис підготовано з допомогою ШІ для перевірки. Результати цієї версії отримано в MongoDB Atlas. Архів із попередньою локальною версією збережено окремо.
